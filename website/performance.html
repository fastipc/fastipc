Performance

FastIPC, iceoryx2, Aeron, ZeroMQ, NNG, Boost.Interprocess, cpp-ipc and the operating system's sockets, run through the same cases on the same machine: a stream between two processes, a broadcast to several, a work queue shared by producers and consumers, and a request-reply service. Every process does the same work with each library, and each library runs in its fastest configuration. The harness fetches and builds every library at a pinned version, and reruns all of it on your machine. Numbers from different machines don't compare, so every chart sets the libraries side by side on each machine. Below them: what to expect beyond these cases, and what each language's binding costs.

Aeron in detail

* Aeron leads FastIPC on Linux x86-64 in the 16-byte stream and the lossless 16-byte broadcast to 4 subscribers; on Linux ARM64 in the lossless 1 KiB broadcast to 1 subscriber.

Both libraries can let a receiver sleep once it has spun briefly on an empty buffer; they differ in what ends the sleep. FastIPC's sender wakes a sleeping receiver as it sends (a futex on Linux, its counterparts on Windows and macOS), so the message is taken as soon as the wake-up lands. Aeron's receive never blocks: between empty polls, the application's idle strategy spins, yields or sleeps for a set time, and nothing cuts a sleep short, so a message that arrives during one waits for it to end. An Aeron receiver that sleeps frees its core at the cost of that delay; one that never sleeps keeps a core 100% busy even while no messages arrive. Every benchmark here polls Aeron without a pause, its lowest-latency setting. Each FastIPC figure is the better of its waiting receive and a polling one, which keeps a core busy like Aeron's.

Aeron also needs its media driver running, as a process of its own (as here) or embedded in one of the applications. The driver's conductor, which moves a publisher's flow-control limit, spins on Windows and backs off into sleeps when idle on Linux x86-64, macOS and Linux ARM64, the fastest setting measured on each. Where it spins, it keeps a second core busy. The receiver polls the same way under either setting.

Batched: FastIPC and Aeron, both ends batching

run.py --batch 16

Everything above sends and receives one message per call, with every library. FastIPC and Aeron also have calls that move several messages at once, so here the two of them run with both ends batching, in the same run, each in its configuration from above. FastIPC's sender calls fipc_send_many with 16 messages, and its receiver fipc_recv_many with room for 16: it waits for the first message, then takes every further one already there, up to 16. Aeron's sender offers 16 messages as one block (aeron_exclusive_publication_offer_block), and its receiver polls with a fragment limit of 16. FastIPC counts the faster of a waiting and a polling receive, as above; Aeron always polls. A round trip has one message at a time to send, so it isn't here. Each cell is FastIPC's figure and how it compares with Aeron's; the last rows batch 64 messages at both ends, and hovering a cell shows both configurations. Batch both ends: a batching sender whose receiver takes one message per call runs slower than one that sends one message per call, as the receiver falls behind and the ring stays full.

Method

bench/alternatives/README.md
  • Processes: every role runs in a process of its own, as IPC does: a stream's sender and receiver, a broadcast's publisher and each subscriber, each producer and consumer, each client and server. No process is pinned to a core.
  • The same work: a sender starts with each message in a buffer of its own; a receiver ends with it in memory of its own, and checks its length. A library that copies receives into the receiver's buffer; one that lends out shared memory (iceoryx2, Aeron, cpp-ipc, FastIPC's zero-copy calls) has the message copied out of it.
  • Each library at its best: every receiver ran twice, once waiting in the library's receive and once polling it in a loop, and the faster counts (iceoryx2's and Aeron's receives never block, so they always poll). FastIPC counts the faster of its copying and zero-copy calls, ZeroMQ and NNG the faster of their local socket and TCP. Each figure's tooltip names the configuration.
  • Configuration: each library runs in its fastest configuration for the pattern on each platform, chosen from sweeps on that platform: its buffer (64 KiB, 512 KiB, 4 MiB and 32 MiB per case, alternating), and for Aeron its media driver's conductor (spinning, which keeps one core busy, or backing off into sleeps when idle, Aeron's default). The configuration with the best geometric mean over the pattern's cases wins (a tie: the smaller buffer, then Aeron's default). The buffer is FastIPC's ring, Aeron's window (half its term), and the bytes of messages iceoryx2's subscriber buffers, Boost's queue, NNG's socket buffers and ZeroMQ's high-water marks hold, at least 8 messages (NNG holds at most 8192). cpp-ipc's queue is fixed and the sockets' buffers are the OS's. Every other option is the library's default. Each platform's configuration is listed below.
  • One message per receive: every library's receive returns one message, so Aeron's subscription polls take one each (a fragment limit of 1; Aeron can take several per poll, which no other library's receive does). The comparison measures each library's synchronization per message, not batching; Batched sets FastIPC and Aeron side by side with both ends batching. A platform whose run took more per poll says so under the configuration table.
  • Windows power throttling: the harness turns it off for itself and for every process it starts, so that Windows doesn't move a process to the efficiency cores or lower its clock when the harness runs without focus.
  • Timing: each run sends for 0.3 s of warm-up and then 1 s that counts; the figure is the median of 3 runs. Throughput is timed by the receiver on the CPU's counter, read once per 64 messages; one round trip in 16 is sampled, chosen at random, the clock reads included. The counter ticks at 24 MHz on the Apple M1, so its round trips are measured in steps of 42 ns.
  • iceoryx2 runs through its Rust API, its own language. Through its C++ binding it ran up to 5 times slower here (16 B one way on Windows: 0.61M against 3.21M messages per second), so the C++ figures aren't shown.
  • Order: every chart and table lists FastIPC first, then the others ranked by their figure's geometric mean over the machines they ran on, the best first, so that the closest rivals sit side by side and no machine's scale outweighs another's.
  • The harness's own cost: about 7 ns per message on the receiving side (a virtual call and the length and sequence checks), the same for every library. FastIPC's own benchmarks run without it: By language, below.
  • Reproduce with python bench/alternatives/deps.py (fetches and builds every library), a CMake build, and run.py: the README has the commands, and results/ the raw medians of every run.

In practice

bench/zig · 2026-10-24/25

What the cases above don't show, from FastIPC's own benchmark suite on the same machines: a receiver that sleeps, the lowest latency, messages longer than the ring, and setting up a connection.

latency-sleep · wakeup

Waking a sleeper

A receiver that waits in a receive call spins for 100 to 250 µs, then sleeps. A message that comes later wakes it in about 28 to 44 µs on Windows, 57 to 60 µs on Linux x86-64 in WSL2, 26 µs on macOS and 35 µs on Linux ARM64, depending on how deeply its core slept.

stream pace

The receiver sets the pace

A receiver that keeps up with its sender pulls the ring's cache lines away from the sender at every look, so each publish waits for them to come back. So a receiver that waits for a stream holds back its first looks (64 pauses on Windows, 32 on Linux x86-64, 512 on ARM64, macOS and Linux, about 4 µs on the M1), which lifts copied 16 to 64 B messages 1.4 to 2.4 times, and 1 KiB on the M1 more than 3 times; one that waits for an answer looks at once. zig build -Dstream_pace=N builds the library for other hardware.

any length

Messages longer than the ring

A message longer than the ring travels in pieces, so its length is limited only by the receiver's buffer, and copy and zero-copy then run alike: 1.5 MiB messages through 512 KiB rings at 8.6 to 14 thousand per second.

fipc_stream_accept · fipc_stream_connect

Connection setup

Listen, connect, accept, close both ends and stop listening, with a 1 MiB ring: 2.5 thousand cycles per second on Linux x86-64, 7.8 thousand on Windows, 4.1 thousand on macOS and 2.2 thousand on Linux ARM64. Set up a connection once, not for each exchange.

Windows throttling · macOS background

Quality of service

Started from a background process, Windows 11 runs a process on its efficiency cores unless power throttling is off for it: 64 KiB messages fall from about 430 to 210 to 280 thousand per second. macOS has its counterpart, the background state, which runs a process and its children on the M1's efficiency cores (copied 1 KiB messages at 7 million per second instead of 27 million). The benchmarks turn the throttling off and leave the background state; an application that needs the speed should do the same.

Lowest latency: busy-polling

For the lowest latency at any message rate, poll instead of waiting: call fipc_recv (or fipc_recv_acquire, or a binding's receive) with timeout 0 in a loop, and call again on FIPC_TIMEOUT. A call that finds nothing makes no system call and reads no clock: it looks at the ring's indices, pauses for a spin hint and looks once more, checks the connection's state and returns, in about 50 ns on x86. The polling thread holds one core at 100%.

Questions

FAQ
What is the fastest IPC library?

It depends on the pattern and the message. FastIPC is the fastest, or level with the fastest, in 28 of the 30 measurements of the case-by-case table; Aeron leads the other 2. Of the libraries here, only FastIPC has all four patterns (stream, broadcast, work queue and service) in shared memory. (Case by case.)

How does FastIPC compare with Aeron?

Aeron is the closest rival. FastIPC has the lower round-trip latency on Linux x86-64 and Windows, and the two are about even on macOS and Linux ARM64. FastIPC leads 16-byte one-way throughput on Windows, macOS and Linux ARM64, and Aeron leads on Linux x86-64 (by 12%). FastIPC leads it at 1 KiB on every platform here. Aeron also works across machines, over UDP. On one machine FastIPC is simpler to set up: Aeron needs a media driver running, as a process of its own or embedded in one of the applications. Either library can let an idle receiver sleep, but a sleeping Aeron receiver sees a new message only when its sleep ends, whereas FastIPC's sender wakes its receiver as soon as it sends. Aeron has no work queue or request-reply service. (Charts above; details in Aeron in detail.)

Is FastIPC faster than ZeroMQ?

Yes, in every one of the 72 measurements where both ran: a 16-byte round trip, for example, is 240 to 478 times as quick. ZeroMQ passes each message through a socket and its own I/O threads, while FastIPC writes it into memory both processes map. ZeroMQ also works across machines; FastIPC works within one.

How does FastIPC compare with iceoryx2?

Both are shared-memory libraries without a broker. FastIPC is faster in every one of the 68 measurements where both ran; its request-reply calls, for example, run 3.1 to 3.6 times as fast. iceoryx2 has no work queue and delivers each request to every server, so its servers don't share a load. It has events and a blackboard, and runs on more platforms (QNX, FreeBSD and others).

How does FastIPC compare with NNG (nanomsg)?

NNG passes each message through its own threads, and every hand-over between threads costs a wake-up, so it is far slower here: a 16-byte round trip is 195 to 1,077 times as quick with FastIPC. NNG works across machines; FastIPC works within one.

Is shared memory faster than a Unix domain socket?

Yes. Here a 16-byte round trip through FastIPC's shared memory is 11 to 20 times as quick as over a Unix domain socket. A socket costs a system call and a copy through the kernel for every send and receive; shared memory needs neither once the connection is set up.

Can I run these benchmarks myself?

Yes. bench/alternatives in the repository fetches and builds every library at the version shown and builds the harness with CMake, and run.py runs every case and writes the medians. The README there has the commands, and the method above says what each case does.
