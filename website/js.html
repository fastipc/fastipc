fipc on npm · import { Listener, Connection } from "fipc"

JavaScript

One Node-API addon for Node.js 22+, Bun and Deno 2: Listener.listen and Connection.connect give listeners and connections with plain, zero-copy and RPC messages. Every call that may wait returns a Promise and leaves the event loop running; a Sync form waits on the calling thread. A call the library refuses fails with a FipcError whose code names the result. TypeScript types included; nothing is compiled when you install it. The package carries the addon and the native library for Windows x64, Linux x64 and ARM64 (glibc 2.34+) and macOS 14.4+ on Apple Silicon.

Server and client

two processes, one name

Start the two in either order, in two terminals (node server.mjs, node client.mjs; bun and deno run -A run them as they are): Connection.connect waits up to its timeout, in milliseconds, for a server to listen and accept; a call without a timeout waits as long as it takes. The pair makes the exchange every example on this site makes, an RPC request with opcode 1 and the payload ping, answered in upper case: this client works with any language's server, and this server with any language's client.

server.mjs
import { Listener } from "fipc";

const listener = Listener.listen("my_channel", 1 << 20); // rings of 1 MiB each way
const conn = await listener.accept(); // waits for a client; the event loop runs meanwhile
const request = await conn.rpcReceive();
await conn.rpcRespond(request.id, request.opcode, 0, request.payload.toString().toUpperCase());
conn.close();
listener.close();
client.mjs
import { Connection } from "fipc";

const conn = await Connection.connect("my_channel", 5000); // waits up to 5 s for the server
await conn.rpcSubmit(1, "ping"); // opcode 1
console.log((await conn.rpcReceive()).payload.toString()); // PING
conn.close();

Plain messages

bytes of any size, no header

Without RPC, a connection carries plain messages: send takes a message of any size, a string (sent as UTF-8), a Buffer or any TypedArray, a DataView or an ArrayBuffer, and receive resolves to each one whole, as a new Buffer. A message longer than the ring travels in pieces and arrives whole. This server echoes every message back until its client leaves, which ends its next receive with FIPC_DISCONNECTED.

echo_server.mjs
import { Listener } from "fipc";

// rings of 1 MiB each way: a power of two, 1 KiB to 2 GiB
const listener = Listener.listen("demo", 1 << 20);
const conn = await listener.accept(); // waits for a client
for (;;) {
  let message;
  try {
    message = await conn.receive();
  } catch (error) {
    if (error.code === "FIPC_DISCONNECTED") break; // the client is gone
    throw error;
  }
  await conn.send(message); // echo, any size
}
console.log("client gone");
conn.close();
listener.close();
echo_client.mjs
import { Connection } from "fipc";

const conn = await Connection.connect("demo", 5000);
for (const word of ["hello", "shared", "memory"]) {
  await conn.send(word);
  console.log((await conn.receive()).toString());
}
conn.close();

Async and Sync calls

the event loop keeps running

A plain call (accept, connect, send, receive, rpcReceive, ...) returns a Promise. It makes the call at once when it needn't wait (a message is there, the ring has room), which costs no more than the Promise; otherwise a thread of the connection's own, one per direction (a listener has one for accepting), waits in the library and settles the promise. libuv's thread pool is never used, so files, DNS and crypto never wait behind FastIPC, and no number of waiting calls starves it.

Calls of one direction run in the order they were made, so sends needn't be awaited one by one. Don't change a buffer you passed to send, or read one you passed to receiveInto, until its promise settles, and don't resize or transfer its ArrayBuffer meanwhile: the call uses the memory in place.

The Sync form (acceptSync, connectSync, sendSync, receiveSync, ...) waits on the calling thread and blocks the event loop meanwhile: the fastest way to make many calls in a tight loop or in a Worker, and with NO_WAIT a way to poll. While an async call of a direction is pending, a Sync call of that direction fails with ERR_FIPC_BUSY.

a receive that waits, and a timer that keeps firing
const timer = setInterval(() => console.log("the event loop runs"), 100);
const message = await conn.receive(); // waits without blocking the timer
clearInterval(timer);
polling once a frame, with the Sync calls
// once a frame: take what has arrived, without waiting
for (;;) {
  let message;
  try {
    message = conn.receiveSync(NO_WAIT);
  } catch (error) {
    if (error.code === "FIPC_TIMEOUT") break; // nothing more this frame
    throw error; // "FIPC_DISCONNECTED": the peer is gone
  }
  handle(message);
}

Errors and timeouts

FipcError, its code

A call the library refuses rejects (in the Sync form, throws) a FipcError: its code is "FIPC_TIMEOUT", "FIPC_DISCONNECTED", "FIPC_CANCELLED", "FIPC_TOO_LARGE", "FIPC_INVALID", "FIPC_NO_MEMORY" or "FIPC_ADDR_IN_USE", the C API's results (result is the number, call the method). A misuse is a TypeError or RangeError, or an Error with the code ERR_FIPC_CLOSED (a closed handle) or ERR_FIPC_BUSY. The timeout comes last, in milliseconds: NO_WAIT (0) doesn't wait, leaving it out (or FOREVER) waits as long as it takes. FIPC_DISCONNECTED is final: close the connection, then accept or connect a new one.

wait at most 100 ms
try {
  handle(await conn.receive(100)); // waits at most 100 ms
} catch (error) {
  if (error.code !== "FIPC_TIMEOUT") throw error; // "FIPC_DISCONNECTED": the peer is gone
}
a buffer of your own: FIPC_TOO_LARGE says how much room
let buffer = Buffer.alloc(4096);
let length;
try {
  length = await conn.receiveInto(buffer);
} catch (error) {
  if (error.code !== "FIPC_TOO_LARGE") throw error;
  buffer = Buffer.alloc(error.length); // the message stays queued: make room, then take it
  length = await conn.receiveInto(buffer);
}

Zero-copy

up to conn.maxPiece bytes

Write a message into the ring and commit it; read one in the ring and release it. sendAcquire resolves to a Uint8Array over room in the ring; sendCommit publishes its first bytes (all, or fewer). receiveAcquire resolves to a Uint8Array over the message, valid until receiveRelease, the next receive or close. When the bytes stop being valid the view is detached, its length 0, so a stale view can never touch the ring; one that can still be reached keeps its connection open. A message of several pieces fails with FIPC_TOO_LARGE and stays queued for receive. Making a view costs more than copying a short message, so in JavaScript zero-copy pays off for long ones.

send in place
const slot = await conn.sendAcquire(5); // room in the ring: a Uint8Array
slot.set(Buffer.from("hello"));
conn.sendCommit(5); // sent; the view is detached
receive in place
const view = await conn.receiveAcquire(); // the message in the ring
handle(view); // read it in place
conn.receiveRelease(); // frees its room; view.length is 0 from now on

RPC

{ id, kind, opcode, status, payload }

Requests carry your opcode; responses echo the request's id and add a status (an int32). Either side may submit. rpcReceive resolves to an object with the payload as a Buffer; rpcReceiveInto(buffer) puts the payload in your buffer and resolves to the object with length in its place. A payload may be empty (left out). Ids are numbers, from 1, increasing (a bigint is taken too). Several requests may be in flight; correlate the responses by id. Use a connection for RPC or for plain messages, not both.

rpc_server.mjs
import { Listener, RPC_REQUEST } from "fipc";

const UPPER = 1;

const listener = Listener.listen("my_channel", 1 << 20);
const conn = await listener.accept();
for (;;) {
  let request;
  try {
    request = await conn.rpcReceive();
  } catch (error) {
    if (error.code === "FIPC_DISCONNECTED") break;
    throw error;
  }
  if (request.kind === RPC_REQUEST && request.opcode === UPPER) {
    await conn.rpcRespond(request.id, request.opcode, 0, request.payload.toString().toUpperCase());
  }
}
conn.close();
listener.close();
rpc_client.mjs
import { Connection, RPC_RESPONSE } from "fipc";

const UPPER = 1;

const conn = await Connection.connect("my_channel", 5000);
const words = ["ping", "shared", "memory"];
// three requests in flight at once; the server answers them in order
const ids = await Promise.all(words.map((word) => conn.rpcSubmit(UPPER, word)));
for (const id of ids) {
  const reply = await conn.rpcReceive();
  console.log(reply.kind === RPC_RESPONSE && reply.id === id, reply.payload.toString()); // true PING, ...
}
conn.close();

Any language on the other end

one protocol

The server.mjs and client.mjs above work with a peer in any of the ten languages: every pair of languages is tested. A Node.js process can hand CPU-heavy work to a worker written in Rust, C++ or Python, or serve as the front end of a native engine, without a socket.

Lifetimes and worker threads

close, cancel, the garbage collector

conn.cancel() makes every call of the connection that waits, then or later, fail with FIPC_CANCELLED. conn.close() ends the connection: pending calls fail with FIPC_CANCELLED, every view is detached, and the peer gets FIPC_DISCONNECTED once it has received what this side sent. listener.close() stops listening and leaves the connections it accepted open. Both work with using (Symbol.dispose).

A listener or connection the program drops is closed when the garbage collector finalizes it; those still open when a worker thread or the process ends are closed then. An idle connection doesn't keep the process alive; a pending call does, until it settles, as a socket would.

A listener or connection belongs to the JavaScript thread that made it, the main thread or a Worker: each worker opens connections of its own. A client and its server may even run in one process, since await listener.accept() and await Connection.connect(name) each wait on a thread of their own. There is no heartbeat and no timeout: a paused or hung peer is not reported, a crashed or killed one as soon as its process has ended.

Node.js, Bun and Deno

Node-API 8 · x86-64-v3 · ARM64 Linux · Apple Silicon

The binding is one Node-API addon, the interface all three runtimes load, so one package serves them: Node.js 22 or newer, Bun, and Deno 2 (which needs --allow-ffi to load an addon, and --allow-read and --allow-env for the binding to find it). The package carries the addon and the native library for every platform in prebuilds/, picks the right one when it loads, and runs no install script. Types come with it, for import and for require.

The binding looks for its addon and the library in the folder FASTIPC_LIB_DIR names, then (in a checkout of the repository) its zig-out build, then the package's prebuilds/<platform>-<arch>/, and for the library last, the system's search. fipc.library and fipc.addon say which files it loaded; the library stays loaded until the process ends.

run the client in each runtime
node client.mjs
bun client.mjs
deno run --allow-ffi --allow-read --allow-env client.mjs
