fastipc

Shared-memory IPC between processes, in any language.

A small Zig library for sending messages between processes on the same machine. Each connection is a pair of lock-free rings that both processes map, plus a local socket that tells each side when the other one has gone. You can use it from C, C++, Zig, Python, C#, Java, Rust, Lua, JavaScript or Go.

Small on purpose

from the architecture

The core is small, and it covers what two local processes usually need from each other: messages of any size, zero-copy, broadcasts, work queues, services with replies, and a prompt report when the other process exits or crashes.

8,324 lines of Zig

The whole library, small enough to read

Everything behind fipc.h, for all three operating systems, is 8,324 lines of Zig. The count includes only code that ends up in the library. Blank lines, comments, tests, test hooks and compile-time checks are left out.

fipc_stream_connect · fipc_stream_accept

Either order, any restart

Start the server or the client first. fipc_stream_connect waits, within its timeout, for a server to listen and accept. Restart either side at any time. The other side receives every message the old process completed, then gets FIPC_DISCONNECTED, and its next fipc_stream_accept or fipc_stream_connect pairs it with the new one.

fipc_result_t

Results you can act on

Every call returns one of eleven result codes. Each code tells you the state of the connection and what to do next. If a send times out because the ring is full, or a receive times out because no message arrived, nothing was sent or taken, and you can call it again. A message too large for your receive buffer stays queued, so you can read it again with a bigger one. A disconnect means the peer is gone, and a server usually handles it by waiting to accept a new connection. All eleven codes.

one copy · one swap

Cheap on the hot path

Sending a message is one copy into shared memory, then a store and an atomic swap to publish it. No locks are taken. The operating system is involved only when the receiver has stopped spinning and gone to sleep, and then the wake-up is a single system call. A background thread watches for the other process to exit, so that check costs the hot path nothing. A 16-byte round trip between two processes takes 125 to 163 ns on the machines we measured, and no library we compared was faster.

Any language on the other end

one protocol · 100 pairs, tested

A process in any of the ten languages can talk to a process in any other, because every binding wraps the same native library and speaks the same protocol. The two sides only have to agree on the connection name and the message format.

All the servers and clients in the quick start do the same thing. The client sends the message ping and the server answers PING. python devtool.py test interop runs every server against every client, each in its own process, on Linux, Windows and macOS.

What it gives you

from include/fipc.h
lock-free rings

Rings in shared memory

Messages go through lock-free ring buffers that both processes map. A connection has two rings, one per direction, each with one writer and one reader (SPSC). The write and read positions sit on separate cache lines, so the writer and the reader don't false-share.

futex · event

Spin, then sleep

A waiting side spins briefly, then sleeps on a futex (Linux), an os_sync address wait (macOS) or a named event (Windows). A publish costs one store and one locked swap. The sleep protocol is built so that a wake-up is never lost.

acquire · commit · release

Zero-copy, or any size

You can write a message directly into the ring and read it in place, 16-byte aligned. The copying calls take messages of any size. A message larger than the ring is sent in pieces and arrives whole. Nothing is allocated per message.

FIPC_DISCONNECTED

Knows when the peer is gone

A local control connection per connection (an abstract AF_UNIX socket, a named pipe, a socket file on macOS) reports the peer's end as soon as its process exits or closes the connection. There is no heartbeat or timeout to tune, and a crash leaves nothing to clean up.

one machine

Local only, on purpose

Zero-copy messages and a peer's end reported without a heartbeat both depend on shared memory and on one kernel that sees both processes. Neither holds across a network, so FastIPC has no network transport. A component that moves to another machine can switch to a network library such as ZeroMQ, whose PAIR, PUB/SUB, PUSH/PULL and REQ/REP sockets correspond to the stream, the broadcast, the queue and the service.

fipc_broadcast_*

Broadcasts (pub/sub)

One publisher and up to 1,024 subscribers, in any processes. Each message is stored once, in memory that every subscriber maps. A lossy subscriber never holds the publisher back. A gated one misses nothing and can read messages in place.

fipc_queue_*

Work queues

Up to 63 producers and 64 consumers, in any processes. Each message goes to one consumer. If that consumer's process ends before acknowledging it, the message goes to another.

fipc_service_*

Services (request and reply)

Up to 64 clients and one server or a pool of up to 64, in any processes. Each request goes to one server, and the replies come back to each client in the order it sent its requests. A request reserves room for its reply, so a server never waits for a client. If a server ends before replying, the request is answered with FIPC_ABANDONED.

protocol v1 · channel v1

A specified protocol

Everything on the wire is written down, so two builds interoperate bit for bit. A bug in one process can't crash the other: each side bounds-checks what it reads from shared memory, which costs a few integer comparisons per message, and a corrupt ring returns FIPC_INVALID.

30 functions

One header

One header of 30 functions in front of a library you can read end to end (how small). The tests are about twice its size.

tests · TSan · chaos · fuzz

Tested under failure

Unit tests and a C-API conformance suite, run in one process and across processes, including peers killed at every step of the handshake. Both also run under ThreadSanitizer. Chaos, soak and fuzz harnesses kill and pause peers, churn connections and feed in corrupt data.

How it works

from docs/protocol.md

A server listens on a name and accepts one client at a time; a client connects to the name. Only processes of the same user can connect.

  1. Set up

    The server's fipc_stream_accept accepts the client, creates a zeroed segment and offers it in a SEGMENT frame. The client's fipc_stream_connect checks the frame and the segment's header, maps it and answers READY. Both run on the calling threads, so a client and its server run on different threads or processes. fipc_stream_connect can return before the server's fipc_stream_accept does; messages sent meanwhile wait in the ring.

  2. Talk

    Messages go through the rings and never touch the control connection. A frame is a 16-byte header and a piece, and never wraps, so every piece is contiguous and the zero-copy calls can hand out pointers into the ring.

  3. End

    When a process closes the connection or exits for any reason, the kernel closes its end of the control connection. The other side reads EOF. Its sends then return FIPC_DISCONNECTED at once, and its receives do so after delivering every message the peer completed.

Quick start

one exchange, every language

Each language has a server file and a client file. Run the server in one process and the client in another. The client sends ping and the server answers in upper case. Every pair makes the same exchange, so a client in any language works with a server in any other (every pair is tested).

Installzig fetch --save git+https://github.com/fastipc/fastipc
server.zig
const std = @import("std");
const fastipc = @import("fastipc");

pub fn main(init: std.process.Init) !void {
    // rings of 1 MiB each way
    const listener = try fastipc.streamCreate(
        init.gpa,
        "my_channel",
        1 << 20,
    );
    defer listener.close();
    // waits for a client
    const conn = try listener.accept(.none);
    defer conn.close();

    var buf: [256]u8 = undefined;
    // .none: no timeout
    const len = try conn.recv(&buf, .none);
    const reply = std.ascii.upperString(&buf, buf[0..len]);
    try conn.send(reply, .none);
}
client.zig
const std = @import("std");
const fastipc = @import("fastipc");

pub fn main(init: std.process.Init) !void {
    const five_s: std.Io.Timeout = .{ .duration = .{
        .raw = .fromSeconds(5),
        .clock = .awake,
    } };
    const conn = try fastipc.streamConnect(
        init.gpa,
        "my_channel",
        five_s,
    );
    defer conn.close();
    try conn.send("ping", .none);
    var buf: [256]u8 = undefined;
    const len = try conn.recv(&buf, .none);
    std.debug.print("{s}\n", .{buf[0..len]}); // PING
}

server.c
#include <ctype.h>
#include <fipc.h>

int main(void)
{
    fipc_listener_t* listener;
    if (fipc_stream_create("my_channel", 1 << 20, &listener) != FIPC_OK) /* rings of 1 MiB each way */
        return 1;
    fipc_conn_t* conn;
    if (fipc_stream_accept(listener, &conn, FIPC_FOREVER) == FIPC_OK) /* waits for a client */
    {
        char buf[256];
        size_t len;
        if (fipc_recv(conn, buf, sizeof buf, &len, FIPC_FOREVER) == FIPC_OK)
        {
            for (size_t i = 0; i < len; i++)
                buf[i] = (char) toupper((unsigned char) buf[i]);
            fipc_send(conn, buf, len, FIPC_FOREVER);
        }
        fipc_close(conn);
    }
    fipc_listener_close(listener);
    return 0;
}
client.c
#include <fipc.h>
#include <stdio.h>

int main(void)
{
    fipc_conn_t* conn;
    fipc_result_t result = fipc_stream_connect("my_channel", &conn, 5000);
    if (result != FIPC_OK)
    {
        fprintf(stderr, "connect: %s\n", fipc_result_str(result));
        return 1;
    }
    char buf[256];
    size_t len;
    if (fipc_send(conn, "ping", 4, FIPC_FOREVER) == FIPC_OK
        && fipc_recv(conn, buf, sizeof buf, &len, FIPC_FOREVER) == FIPC_OK)
        printf("%.*s\n", (int) len, buf); /* PING */
    fipc_close(conn);
    return 0;
}

server.cpp
#include <cctype>
#include <string>

#include <fipc.hpp>

int main()
{
    auto listener = fipc::stream_create("my_channel", 1 << 20);  // rings of 1 MiB each way
    if (!listener)
        return 1;
    auto conn = listener->accept();  // waits for a client
    if (!conn)
        return 1;
    std::string message;
    if (!conn->receive(message))
        return 1;
    for (char& c : message)
        c = static_cast<char>(std::toupper(static_cast<unsigned char>(c)));
    return conn->send(message) ? 0 : 1;
}
client.cpp
#include <chrono>
#include <cstdio>
#include <string>

#include <fipc.hpp>

int main()
{
    auto conn = fipc::stream_connect("my_channel", std::chrono::seconds(5));
    if (!conn)
    {
        std::fprintf(stderr, "connect: %s\n", conn.error().name());
        return 1;
    }
    std::string reply;
    if (!conn->send("ping") || !conn->receive(reply))
        return 1;
    std::printf("%s\n", reply.c_str());  // PING
    return 0;
}

package main

import (
	"bytes"
	"log"

	"github.com/fastipc/fastipc/bindings/go/fipc"
)

func main() {
	listener, err := fipc.CreateStream("my_channel", 1<<20) // rings of 1 MiB each way
	if err != nil {
		log.Fatal(err)
	}
	defer listener.Close()
	conn, err := listener.Accept(fipc.Forever) // waits for a client
	if err != nil {
		log.Fatal(err)
	}
	defer conn.Close()
	message, err := conn.Receive(fipc.Forever)
	if err != nil {
		log.Fatal(err)
	}
	if err := conn.Send(bytes.ToUpper(message), fipc.Forever); err != nil {
		log.Fatal(err)
	}
}

One Node-API addon for Node.js, Bun and Deno. Calls on Listener and Connection that may wait return Promises that never block the event loop, and each has a Sync form. Zero-copy views detach when they end. TypeScript types are included.

Go

fipc

One package that loads the library through purego, so no cgo is needed. Listener and Conn are safe from any goroutine, like a net.Conn. Errors work with errors.Is, timeouts are time.Durations, and a context can cancel a call.

Platform support

from docs/platform-support.md

FastIPC supports recent systems only. That lets the code use modern APIs and instructions directly, with no fallbacks or feature probes.
